# 开发指南

## 环境

- Python 3.11+
- 推荐使用独立虚拟环境

```bash
pip install -e .
```

如需开发工具，可按 `pyproject.toml` 和 `requirements.txt` 安装当前项目声明的依赖。不要依据旧文档假设存在未声明的文档构建或发布流程。

## 代码边界

- `core/orchestrator.py` 是兼容入口，主要实现位于 `core/orchestration/`。
- TaskGraph 的结构与状态转换放在 `core/`。
- 模型、子进程、工作区、追踪和插件宿主放在 `runtime/`。
- 数据持久化放在 `storage/`，不要绕过 store 随意写运行数据库。
- 工具通过 `tools/` 的注册和分发接口接入。
- CLI 只负责参数、命令路由和展示，不应复制编排业务逻辑。

新增能力时同步维护 [能力状态表](status.md)，并明确它是可用、部分实现还是未实现。

## 验证顺序

先执行与修改直接相关的窄测试，再扩大范围：

```bash
python -m compileall -q src/AstralNexus
pytest -q tests/<relevant_test_file>.py
pytest -q
```

需要模型密钥、网络、外部工具或平台能力的测试应明确标记条件，不能把“未配置环境”误报为框架逻辑通过或失败。

## 测试重点

对编排与恢复修改，至少覆盖：

- 正常成功路径。
- 解析或校验失败及有限重试。
- 取消、需求变化和所有权丢失。
- 并发结果处理和图补丁一致性。
- 恢复预算、停滞检测与最终失败。
- 节点完成但交付验收失败的情况。

对文档和 CLI 修改，应核对 argparse 中的真实参数，并运行相应的 `--help` 或静态入口检查。

## 数据库变更

新增字段或表时，应处理已有运行数据库，保留迁移或兼容读取路径，并为恢复场景编写测试。`runtime_state.json` 不能作为规避数据库迁移的长期替代品。

## 提交前检查

- 没有真实密钥、运行数据库或大体积产物进入源码包。
- 示例命令在当前 CLI 中存在。
- 新配置字段确实被加载器消费。
- 新的产品能力在入口、实现和测试之间能互相对应。
- 文档未把逻辑资源标签宣传为物理隔离保证。
