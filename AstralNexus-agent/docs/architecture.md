# 天枢系统架构文档

## 概述

天枢系统是一个面向超长程复杂任务的动态异构群体智能协同推理引擎。它采用了分层架构设计，将复杂的任务分解为可管理的子任务，并通过多个专门的智能体协同工作来完成这些任务。

## 架构层次

### 1. 意图解析层 (Intent Parsing Layer)

这一层负责将用户的高层目标解析为具体的任务合同，包括：
- 目标定义
- 硬约束条件
- 验收标准
- 风险评估
- 数据敏感度等级
- 时间和成本预算

### 2. 语义任务图层 (Semantic Task Graph Layer)

这是系统的核心，将复杂任务表示为动态有向无环图(DAG)：
- 节点代表子任务
- 边代表依赖关系、证据流、控制流、产物流和通信关系
- 支持任务状态的动态更新和转换

### 3. 异构角色层 (Heterogeneous Roles Layer)

管理系统中的不同能力智能体角色：
- Planner (规划者)
- Researcher (研究员)
- Coder (编码员)
- Verifier (验证员)
- Reviewer (审查员)
- Memory Curator (记忆管理员)
- Resource Broker (资源经纪人)
- Recovery Agent (恢复代理)

### 4. 认知拓扑路由层 (Cognitive Topology Routing Layer)

根据任务语义、依赖关系、失败状态、资源约束和历史表现，动态选择：
- 稀疏通信边
- 子任务执行者
- 最小上下文包
- 资源层级与模型选择
- 验收条件和失败恢复策略

### 5. 分层任务记忆层 (Hierarchical Task Memory Layer)

建立三层记忆结构以保证长链任务中的目标一致性和状态连续性：
- 短期工作记忆：当前执行节点、最近消息、当前约束
- 中期情景缓存：任务图、事实、决策、产物、故障
- 长期知识沉淀：可复用经验、项目惯例、失败模式、角色表现

### 6. 端云自适应调度层 (Edge-Cloud Adaptive Scheduling Layer)

根据数据敏感度、实时性、复杂度、成本和模型能力，动态选择：
- 本地资源：隐私高、成本低、能力有限
- 边缘资源：时延较低、数据可控
- 云端资源：能力强、成本高、隐私约束强

### 7. 观测评测层 (Observation and Evaluation Layer)

输出各种指标和报告：
- 任务图和节点状态变化
- 角色调度和资源选择
- Token、时间、成本消耗
- 失败恢复过程和结果
- 最终交付物和验证结果
- 可视化报告

## 核心组件详解

### 任务图 (Task Graph)

任务图是天枢的全局状态中枢，将长程任务从"线性对话历史"转化为"可查询、可回滚、可验收的结构化过程"。

#### 节点属性
- `node_id`: 节点唯一标识符
- `goal`: 子任务目标
- `role`: 负责执行的角色
- `status`: 状态 (pending, running, passed, failed, blocked, superseded)
- `dependencies`: 依赖的其他节点
- `constraints`: 约束条件
- `inputs`: 输入数据
- `outputs`: 输出产物
- `risk_level`: 风险等级
- `sensitivity`: 数据敏感度
- `resource_tier`: 资源层级
- `retry_count`: 重试次数
- `acceptance`: 验收条件

#### 边类型
- `depends_on`: 执行依赖
- `evidence_for`: 证据支撑
- `produces`: 产物生成
- `revises`: 变更修订
- `verifies`: 验收验证
- `blocks`: 阻塞关系
- `communicates_to`: 稀疏通信关系

### 认知拓扑路由器 (Router)

路由器负责决定任务执行的各个方面：
1. **任务语义分析**：子目标类型、关键词、领域、预期产物
2. **图结构分析**：依赖深度、阻塞节点、上下游影响范围
3. **风险状态评估**：失败次数、测试失败、需求变更、证据冲突
4. **角色能力匹配**：角色专长、历史成功率、可用工具集
5. **资源约束考虑**：隐私等级、上下文长度、时延、成本

输出结果包括：
- 执行节点集合
- 节点对应角色
- 最小上下文包
- 稀疏通信边
- 资源层级与模型选择
- 验收条件和失败恢复策略

### 低熵结构化通信协议 (Message Protocol)

为了减少通信冗余，天枢采用结构化消息协议：
```json
{
  "node_id": "T-012",
  "role": "verifier",
  "status": "pass",
  "summary": "不超过 120 字",
  "claims": [
    {
      "text": "新增恢复测试已覆盖超时分支",
      "evidence": ["artifact://logs/pytest_T-012.txt"],
      "confidence": 0.86
    }
  ],
  "artifacts": ["file://tests/test_recovery.py"],
  "risks": ["仍缺少网络异常集成测试"],
  "next_actions": [
    {
      "type": "spawn",
      "target": "T-013",
      "reason": "需要补充集成测试"
    }
  ],
  "budget_used": {
    "prompt_tokens": 0,
    "completion_tokens": 0,
    "wall_time_s": 0
  }
}
```

通信原则：
1. 只传递与下游任务相关的 facts、artifacts、constraints
2. 原始长轨迹进入 artifact，不进入主上下文
3. 每条结论必须绑定证据和置信度
4. 每个节点必须输出可验收状态
5. 失败节点必须给出失败类型、影响范围和建议恢复动作

### 分层任务记忆 (Memory Federation)

三级任务记忆系统：
1. **短期工作记忆**：当前执行节点、最近消息、当前约束（单轮/短窗口）
2. **中期情景缓存**：任务图、facts、decisions、artifacts、faults（单个 run）
3. **长期知识沉淀**：可复用经验、项目惯例、失败模式、角色表现（跨 run）

关键机制：
1. **事实锚定**：关键目标、约束、决策和证据写入 facts 表，并绑定来源
2. **压缩唤醒**：上下文压缩后，可按 node_id、fact_query、artifact_query 唤醒被压缩内容
3. **约束版本化**：需求变更生成新版本约束，旧约束不直接覆盖，避免目标漂移
4. **证据链追踪**：每个重要 claim 都必须指向产物、日志、文档片段或测试结果
5. **子图恢复**：失败或变更时，只重算受影响子图，保留无关子图成果

### 端云自适应调度器 (Resource Scheduler)

调度器根据任务属性选择推理资源和执行环境。

资源层级：
- **本地**：敏感数据处理、代码执行、快速校验、轻量摘要（隐私高、成本低、能力有限）
- **边缘**：中等复杂推理、局部检索、企业内网任务（时延较低、数据可控）
- **云端**：复杂规划、长文综合、跨域推理、最终审查（能力强、成本高、隐私约束强）

调度策略：
```
score(resource, node) =
    capability_match
  - latency_penalty
  - cost_penalty
  - privacy_penalty
  + reliability_score
  + context_fit_score
```

### 故障注入与自恢复 (Fault Recovery)

故障注入是天枢的重要特性，系统不仅能完成任务，还能在任务被打断后自动恢复。

故障类型：
1. **需求变更**：中途新增约束、修改验收标准
2. **节点失败**：子任务超时、输出格式错误、结果置信度低
3. **工具失败**：测试失败、命令失败、网络失败
4. **记忆缺失**：隐藏历史上下文或压缩后丢失细节
5. **资源降级**：云模型不可用、边缘服务超时

恢复流程：
1. Fault Detector 识别故障类型
2. Impact Analyzer 标记受影响节点和下游依赖
3. Recovery Agent 生成恢复计划
4. Router 重路由受影响子图
5. Verifier 重新验收产物
6. Reporter 记录恢复耗时、额外 token、最终状态

## 数据存储

天枢使用 SQLite 作为主要存储后端，保证轻量、可部署、可回放：

存储结构：
- `runs`: 目标、开始结束时间、状态、全局约束
- `nodes`: 子任务节点、角色、状态、重试次数、资源层级
- `edges`: 依赖边、证据边、控制边、通信边
- `messages`: 结构化低熵消息
- `facts`: 任务事实、来源、置信度、验证时间
- `artifacts`: 产物路径、hash、责任节点、验收状态
- `metrics`: token、时间、成本、压缩率、失败恢复
- `faults`: 异常、需求变更、节点失效、恢复结果

## 性能优化

### 动态稀疏拓扑路由

通过只在必要时建立通信连接，大大减少了通信复杂度：
- 传统全连接多智能体：O(N^2 * L_free_text)
- 天枢稀疏拓扑：O(E_sparse * L_structured)

其中 E_sparse << N^2 且 L_structured << L_free_text

### 最小上下文检索

只给子任务注入必要上下文，避免长程任务中的 token 冗余。

### 受影响子图重算

需求变更或节点失败后，不全量重跑，而是定位受影响子图：
- 受影响节点数为 S，依赖边数为 E_s
- 恢复复杂度约为 O(S + E_s)
- 优于全图重算 O(N + E)

## 安全性考虑

1. **数据隐私**：高敏文件只在本地处理，云端只接收脱敏摘要
2. **访问控制**：角色有明确权限边界，避免无序通信和越权执行
3. **审计跟踪**：所有操作都有详细日志记录，便于追溯和审计
4. **资源隔离**：不同任务在独立环境中执行，防止相互干扰

## 可扩展性

1. **插件架构**：支持通过插件扩展新角色、新工具、新资源
2. **模块化设计**：各组件松耦合，便于独立开发和测试
3. **配置驱动**：大部分行为通过配置文件控制，无需修改代码
4. **API 接口**：提供标准 API 接口，便于与其他系统集成

## 监控和运维

1. **实时监控**：通过仪表板实时查看任务执行状态
2. **日志记录**：详细的日志记录便于问题排查
3. **性能指标**：收集各种性能指标用于优化
4. **健康检查**：定期检查系统健康状态
5. **自动恢复**：部分故障可自动恢复，减少人工干预
